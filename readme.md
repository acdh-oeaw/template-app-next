# template-app-next

Template for Next.js apps at ACDH, using Bun.

## Getting started

```sh
bun install
bun run dev
```

In a new repository created from the template, ask an agent to set up the app, which follows the
[`setup` skill](.claude/skills/setup/SKILL.md): it asks which [optional features](#optional-features) to keep, removes
the others, and replaces the template's name and metadata.

`bun install` also creates `.env.local` (see [Environment variables](#environment-variables)) and generates route types,
including the search params of pages with a `search-params.ts`.

The `prepare` script sets `BUN_OPTIONS=--bun`, because `run.bun` in `bunfig.toml` doesn't apply to lifecycle scripts, so
`next typegen` would run with Node.js. Remove it once [oven-sh/bun#44584](https://github.com/oven-sh/bun/issues/44584)
is fixed.

## Environment variables

All environment variables are defined as Valibot schemas in [`lib/env/schema.ts`](lib/env/schema.ts), which is the
single source of truth. A removable feature defines its variables in an `env-schema.ts` next to its code, like
[`lib/mail/env-schema.ts`](lib/mail/env-schema.ts), which `lib/env/schema.ts` spreads into its schema, so that
removing the feature leaves a type error at the spread.

- **Public variables** start with `NEXT_PUBLIC_`. They are validated when bundling, and inlined into client and server
  bundles at build time. Import them from `#/lib/env/public.ts`.
- **Server variables** are validated when first read, and all of them at server startup. Import them from
  `#/lib/env/server.ts`. A server variable that is read while prerendering must also be provided at build time.

Don't read `process.env` directly, the linter only allows it in `lib/env/`.

`bun run env:sync` adds missing variables to `.env.local`, with their descriptions and generated development values.
It never changes existing entries, unless you pass `--force`, which overwrites the whole file.

## Local services

Third-party services that the app needs in local development are defined in [`docker/compose.yaml`](docker/compose.yaml),
like [Mailpit](https://mailpit.axllent.org), which receives the mail that the app sends, and shows it at
http://localhost:8025. The [`Dockerfile`](Dockerfile) only builds the production image.

```sh
docker compose --env-file .env.local --file docker/compose.yaml up --detach
```

Services read their variables from `.env.local`, so a value that a service and the app share, like an API key or a port,
is defined once in [`lib/env/schema.ts`](lib/env/schema.ts) and generated by `bun run env:sync`. Reference
variables as `${NAME:?}`, so `docker compose` fails when one is missing. `name` is set, because the project name
otherwise defaults to the folder name, and containers and volumes of different apps would clash.

## Optional features

[`configs/features.ts`](configs/features.ts) lists the features that apps can remove, like the contact form, with their
files, dependencies and local services. Remove a feature rather than disabling it: ask an agent to remove it, which
follows the [`remove-feature` skill](.claude/skills/remove-feature/SKILL.md), or follow the steps there by hand.
`bun test` checks that the list matches the repository.

## Contact form

[`app/[locale]/contact/`](app/[locale]/contact/) is an example of the [layering in `AGENTS.md`](AGENTS.md#services): the
server action validates, rate limits and translates, and calls `sendContactMessage()` from
[`services/contact/`](services/contact/), which sends the mail with nodemailer, through the `Mailer` from
[`lib/mail/`](lib/mail/). A hidden honeypot field catches simple bots. Deployments need `CONTACT_FORM_RECIPIENT`.
The `EMAIL_*` variables default to the smtp server of the ÖAW, which accepts mail from the ACDH cluster without
credentials, and sends from `noreply@oeaw.ac.at`.

## Search

[`app/[locale]/search/`](app/[locale]/search/) searches a [Typesense](https://typesense.org) collection through
`searchDocuments()` from [`services/search/`](services/search/), with the client from
[`lib/typesense/`](lib/typesense/). It is a skeleton to build on. In local development, start Typesense with
`docker compose`, see [Local services](#local-services), and index the sample documents:

```sh
bun run search:index
```

Until the collection exists, the page says that the search index is not available yet.

## App shell

The header and footer are rendered in [`app/[locale]/layout.tsx`](app/[locale]/layout.tsx), and each page renders its own
`<MainContent>`.

That file is the root layout, so a nested layout cannot remove the shell. If some pages need a different one, like a
full-height page with its own scroll area and a different footer, move the current shell into a route group:

```
app/[locale]/
  layout.tsx            html, providers, metadata
  (default)/
    layout.tsx          current shell: min-h-full, header, footer
    (index)/page.tsx
    imprint/page.tsx
    not-found.tsx
  (fullscreen)/
    layout.tsx          h-full shell, different footer
    viewer/page.tsx
```

Move `not-found.tsx` as well, so that pages calling `notFound()` keep the shell. Urls that match no route render
[`app/global-not-found.tsx`](app/global-not-found.tsx), which renders the shell itself. If `next build` then fails with
type errors in `.next/dev/types/validator.ts`, delete that file: it still points to the old paths, and
`bun run types:generate` does not update it.

## Color scheme

The switcher in [`components/color-scheme/`](components/color-scheme/) offers system, light and dark, and is unstyled.
The choice is stored in `localStorage`, because reading a cookie would make the root layout dynamic. An inline script
sets `data-color-scheme` on `<html>` before first paint, and that attribute is the single source of truth for the
switcher.

To remove it, delete `components/color-scheme/` and `e2e/color-scheme.test.ts`, remove `<ColorSchemeScript />` and
`suppressHydrationWarning` from `components/html-document.tsx`, `<ColorSchemeSwitcher />` from `components/header.tsx`, and the
`data-color-scheme` rules from `styles/index.css`.

## Translations

Messages are written in the source locale, with `useExtracted()` or `getExtracted()` from next-intl, and extracted into
`messages/*.po`. `next dev` and `next build` extract them, and `bun run i18n:extract` does so without starting Next.js.
Entries with an empty `msgstr` still need a translation.

## Localized urls

Pages are in `app/[locale]/`, and every url starts with a language prefix, like `/en/about`. Routes in `href()` leave
out the `[locale]` segment, and `<Link>`, `redirect()` and `getPathname()` from `lib/navigation/navigation.ts` add the
prefix back. Apps that don't need a url per language have three options.

### Locale from a cookie

Set `localePrefix: { mode: "never" }` in `lib/i18n/routing.ts`, and remove `prefixes`. Pages stay in `app/[locale]/`:
the proxy rewrites `/about` to the locale from the cookie or the `Accept-Language` header, and redirects prefixed urls,
like `/en-GB/about`, to `/about`. `href()` and its routes are unchanged.
[next-intl documents this mode](https://next-intl.dev/docs/routing/configuration#locale-prefix-never) for a locale from
a cookie, and for one locale per domain. Because urls are no longer unique per locale:

- Remove the `hreflang` alternates: delete `lib/i18n/get-alternate-languages.ts`, remove `alternates.languages` from
  `createPageMetadata()`, and list each page once, without alternates, in `app/sitemap.ts`
- The locale switcher links to the internal prefix, like `/de-AT/about`, which the proxy redirects to `/about`
- Update the end-to-end tests, which visit prefixed urls, and remove the ones for canonical and alternate urls in
  `e2e/i18n.test.ts`

### One language, with a prefix later

Keep one locale in `lib/i18n/locales.ts`, delete the other message files, like `messages/de.po`, and set
`localePrefix: { mode: "as-needed", prefixes }` in `lib/i18n/routing.ts`. The default locale has no prefix, so no url
has one, and `/en/about` redirects to `/about`. `href()` and its routes are unchanged, and adding a language later only
adds urls with its prefix. next-intl does not document this case, and the proxy still runs for every page.

- Delete `components/locale-switcher/` and `e2e/locale-switcher.test.ts`, and remove `<LocaleSwitcher />` from
  `components/header.tsx`
- Replace the removed locale in `lib/navigation/navigation.test-d.tsx`
- Update the end-to-end tests, which visit prefixed urls, and test removed locales

### One language, without i18n routing

[next-intl recommends this](https://next-intl.dev/docs/getting-started/app-router/without-i18n-routing) for apps
without a url per language: no `[locale]` segment and no proxy, and next-intl only provides the messages. `href()` takes
the routes as they are, and the navigation functions wrap Next.js instead of next-intl. Until step 5,
`bun check` reports every `href()` call, because no route starts with `/[locale]` anymore.

1. Move everything in `app/[locale]/` to `app/`, run `bun run types:generate`, and update `PageProps<"/[locale]/…">`,
   `LayoutProps<"/[locale]">`, `RouteContext<"/[locale]/…">`, imports from `#/app/[locale]/`, and the paths in
   `configs/features.ts`, which `bun test` checks. If `bun check` reports errors in `.next/dev/types/validator.ts`,
   delete it
2. In `app/layout.tsx` and `app/og-image/route.tsx`, remove `generateStaticParams()`, the `params` and the
   `hasLocale()` checks, and use `defaultLocale`
3. Keep one locale in `lib/i18n/locales.ts`, delete the other message files and content, like `messages/de.po` and
   `content/de/`, and return `defaultLocale` from `lib/i18n/request.ts`, instead of reading `next/root-params`
4. Delete `proxy.ts`, `lib/i18n/routing.ts` and `components/locale-switcher/`, and remove `<LocaleSwitcher />` from
   `components/header.tsx`
5. In `lib/navigation/href.ts`, change the root param of `Routes` from `"locale"` to `never`
6. In `lib/navigation/navigation.ts` and `lib/navigation/navigation-hooks.ts`, wrap `next/navigation` instead of
   next-intl, without the `Link` export. Keep the `locale` param of `getPathname()` and `redirect()`, so that their
   callers stay unchanged: `getPathname()` returns the href, and `redirect()` ignores the locale. The router accepts
   relative hrefs with all options of `next/navigation`
7. In `components/link.tsx`, render `next/link`, and remove the `locale` prop. Remove `Link` from
   `#/lib/navigation/navigation.ts` from `linkPaths` in `configs/oxlint.config.ts`
8. Remove the Open Graph `alternateLocale` from `lib/metadata/create-page-metadata.ts`, which is always empty, and use
   `/og-image` as the url of the Open Graph image instead of `prefixes`.
   Optionally, remove the `hreflang` alternates, which now only list the page itself and `x-default`: delete
   `lib/i18n/get-alternate-languages.ts`, and remove `alternates.languages` from `createPageMetadata()` and
   `app/sitemap.ts`
9. In `lib/navigation/navigation.test-d.tsx`, remove the cases for the `locale` of `<Link>` and the router, and replace
   the removed locale. Update the fixture path in `AGENTS.md` and this readme
10. Delete `e2e/i18n.test.ts` and `e2e/locale-switcher.test.ts`, remove the locale prefixes and the tests for other
    locales from the other end-to-end tests, and update comments that mention `[locale]`, next-intl routing or locale
    prefixes. This includes the tests for invalid and internal locales in `e2e/errors.test.ts`, whose `test.fail()`
    cases pass without i18n routing, and the test for reciprocal alternates in `e2e/seo.test.ts`

## End-to-end tests

End-to-end tests live in `e2e/` and run with Playwright in Chromium, Firefox and WebKit, against a production build
started by Playwright, or an already running server on port 3000. Set `PORT` to use a different port.

The `instant()` helper from `@next/playwright` asserts what is visible immediately on a page load or client navigation,
before request-time content streams in. It needs the testing API, which `next dev` includes, and `next build` only with
`BUILD_TARGET=e2e`. Playwright sets this for the build it starts, so an already running production server must be
built with it too. The same goes for test fixtures, pages in `app/[locale]/e2e/` that respond with 404 unless built with
`BUILD_TARGET=e2e`.

```sh
bun run test:e2e:install
bun run test:e2e
```

Visual snapshots from `toHaveScreenshot()` depend on the operating system, fonts and browser builds, so they are only
compared in CI, and local runs skip these assertions. To create or update them, push the branch, then run the following
command with the [GitHub CLI](https://cli.github.com) installed. It runs the workflow with `update-snapshots`, waits for
it, and replaces `e2e/snapshots/` with the result for you to review and commit.

```sh
bun run test:e2e:update-snapshots
```

To download the snapshots of a run that has already finished, for example after a failed download, pass its id with
`--run <id>`.

## Continuous integration

[`.github/workflows/validate.yaml`](.github/workflows/validate.yaml) runs static checks and end-to-end tests on pull
requests and pushes to `main`. [`.github/actions/setup`](.github/actions/setup/action.yaml) installs dependencies, and
the Bun version from `devEngines` in `package.json`. This is `canary` until a Bun release includes `bun lint`.

`bun run env:sync` does nothing in CI, so add variables that are required for the build to the `env` of the `e2e` job.
When a test fails, the Playwright report is uploaded as a workflow artifact.

## Docker

[`.dockerignore`](.dockerignore) is an allowlist: when the build needs a new top-level file or folder, add it there.

The Bun version is passed as `BUN_VERSION` build arg, and has no default: it comes from `devEngines` in `package.json`.
Image tags are exact versions or `canary`, so a range resolves to the newest matching release with `bun pm view`.

Public and build-time variables are passed to `docker build` as a single `dotenv` secret. Secrets don't invalidate the
build cache, so the sha256 hash of the secret must be passed as `DOTENV_HASH` build arg, and the build fails if it
doesn't match.

The deployment id for [version skew protection](https://nextjs.org/docs/app/guides/self-hosting#version-skew) is
passed as `NEXT_DEPLOYMENT_ID` build arg. It must change whenever the build output does, so it combines the git commit
hash with the hash of the `dotenv` secret, which is shortened because the deployment id is added to asset urls.

```sh
bun_version="$(jq -r '.devEngines.runtime.version' package.json)"
[ "$bun_version" = canary ] || bun_version="$(bun pm view "bun@$bun_version" version)"

docker build \
  --secret id=dotenv,src=.env.production.local \
  --build-arg BUN_VERSION="$bun_version" \
  --build-arg DOTENV_HASH="$(sha256sum .env.production.local | cut -d " " -f 1)" \
  --build-arg NEXT_DEPLOYMENT_ID="$(git rev-parse HEAD)-$(sha256sum .env.production.local | cut -c 1-12)" \
  .
```

In GitHub Actions:

```yaml
- id: config
  run: |
    bun_version="$(jq -r '.devEngines.runtime.version' package.json)"
    [ "$bun_version" = canary ] || bun_version="$(bun pm view "bun@$bun_version" version)"
    echo "bun-version=$bun_version" >> "$GITHUB_OUTPUT"

- id: dotenv
  env:
    NEXT_PUBLIC_APP_BASE_URL: ${{ vars.NEXT_PUBLIC_APP_BASE_URL }}
    NEXT_SERVER_ACTIONS_ENCRYPTION_KEY: ${{ secrets.NEXT_SERVER_ACTIONS_ENCRYPTION_KEY }}
  run: |
    file="${{ runner.temp }}/dotenv"
    printf 'NEXT_PUBLIC_APP_BASE_URL=%s\nNEXT_SERVER_ACTIONS_ENCRYPTION_KEY=%s\n' \
      "$NEXT_PUBLIC_APP_BASE_URL" "$NEXT_SERVER_ACTIONS_ENCRYPTION_KEY" > "$file"
    echo "file=$file" >> "$GITHUB_OUTPUT"
    echo "hash=$(sha256sum "$file" | cut -d " " -f 1)" >> "$GITHUB_OUTPUT"
    echo "deployment-id=${{ github.sha }}-$(sha256sum "$file" | cut -c 1-12)" >> "$GITHUB_OUTPUT"

- uses: docker/build-push-action@v7
  with:
    secret-files: dotenv=${{ steps.dotenv.outputs.file }}
    build-args: |
      BUN_VERSION=${{ steps.config.outputs.bun-version }}
      DOTENV_HASH=${{ steps.dotenv.outputs.hash }}
      NEXT_DEPLOYMENT_ID=${{ steps.dotenv.outputs.deployment-id }}
```

Server variables that are only read at runtime are passed to the container, not to `docker build`.

Rate limiting finds the client address in the `x-forwarded-for` header, so set `TRUSTED_PROXY_COUNT` to the number of
reverse proxies in front of the app, like `1` behind a Kubernetes ingress. Otherwise clients can choose their address.
The default store of rate limiters is in memory, so each replica counts on its own. With several replicas, use a
shared store, like Valkey, see `RateLimitStore` in [`lib/rate-limit/rate-limiter.ts`](lib/rate-limit/rate-limiter.ts).

Kubernetes probes use `/api/health/live` and `/api/health/ready`, which respond with `200` while the server is up.
Liveness failures restart the container, so the liveness endpoint only checks the process itself. Readiness failures
stop traffic to the pod, so checks for dependencies like a database belong in the readiness endpoint.

```yaml
livenessProbe:
  httpGet:
    path: /api/health/live
    port: 3000
readinessProbe:
  httpGet:
    path: /api/health/ready
    port: 3000
```

## Upgrading Next.js

Public variables are inlined with a getter on `compiler.define` in [`next.config.ts`](next.config.ts), which relies on
two undocumented behaviours. After upgrading, check that:

- `bun run types:generate` (`next typegen`) still succeeds without public variables, i.e. it doesn't read
  `compiler.define`
- editing a public variable in `.env.local` while `bun run dev` is running updates the page without a restart, i.e.
  `next dev` still reads `compiler.define` again when `.env*` files change

Our patch in [`patches/`](patches/) makes Next.js type generation also write the pages, with their params and the
codecs of their `search-params.ts`, to `.next/types/navigation.d.ts`, which `href()` reads. Re-create it with
`bun patch next` for the new version. `bun check` fails if the patch is missing, because the type tests in
`lib/navigation/navigation.test-d.tsx` use the generated routes. Also check that `bun run dev` adds a page to
`.next/types/navigation.d.ts` (not `.next/dev/types`) when it is added while the server runs.

The patch also backports [facebook/react#37814](https://github.com/facebook/react/pull/37814) to the React builds that
Next.js bundles in `dist/compiled/react-dom*/`. Without it, with `cacheComponents`, a client navigation away from a
page that has not hydrated yet can hide the layout content after it, like the footer. Drop that part once the bundled
React includes the fix, which `16.5.0-canary.59` does: check that `hideOrUnhideDehydratedBoundary` in
`node_modules/next/dist/compiled/react-dom/cjs/react-dom-client.production.js` also checks for `"/&"`.

The `dev` script sets `BUN_OPTIONS=--no-env-file`, so that Next.js, not Bun, loads `.env` files and can reload them.
Remove it once [oven-sh/bun#47916](https://github.com/oven-sh/bun/issues/47916) is fixed.
